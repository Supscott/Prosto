# Agent Guidelines & Project Knowledge: Prosto Browser

Welcome to the **Prosto** project. This file provides operational rules, architectural standards, and workflow guidelines for all AI coding agents working on this codebase.

---

## Pre-Flight Checklist (Start of Non-Trivial Tasks)

> [!IMPORTANT]
> **BEFORE writing code or planning any implementation:**
> 1. Read [`LESSONS.md`](LESSONS.md) to review active high-signal gotchas and traps discovered on this codebase.
> 2. Run `rtk tools/verify.sh` to ensure a green baseline before starting changes.
> 3. Read [`TASKS.md`](TASKS.md): open work shared by all agents. When you start a listed task, move it to *In progress* with your branch; when you finish, delete it and add any follow-up you leave behind (one line each).

## Core Rules for Coding Agents

### 1. Clarification & Inquiries (Уточнение сценариев и параметров)
- **Bug reproduction**: When a user reports a bug with generic or symptomatic descriptions (e.g. "sometimes X happens", "icon is wrong", "gesture breaks"), **ask the user to clarify the exact reproduction scenario/steps** if doing so will save investigation time, rather than guessing across multiple speculative paths (e.g. cross-domain navigation vs opening a new tab vs restoring a session).
- **UI & Cosmetic tweaks (Context-First Inquiries)**: When asked to adjust subjective UI properties (e.g. "make spacing slightly smaller", "tweak padding"), **inspect the code/tokens first to find the current value** (e.g. `8.dp`), and offer concrete options (*"Currently spacing is 8.dp. Should we try 4.dp or 6.dp?"*). Never ask raw, context-free questions like *"How many dp do you want?"*.

### 2. CLI Execution & Verification
- **Prefix commands with `rtk`**: Use `rtk git status`, `rtk git diff`, `rtk tools/verify.sh` to minimize token overhead.
- **Fast verification**:
  - `rtk tools/verify.sh`: Invariants + core coordination and engine tests (~20s).
  - `rtk tools/verify.sh --ui`: Invariants + UI previews and bottom dock tests (~25s).
  - `rtk tools/verify.sh --all`: Full unit test suite (`testDebugUnitTest`), then Android Lint (`lintDebug`).
  - `rtk tools/verify.sh --changed`: Invariants + the test classes added or edited on the branch (vs `main`) or in the working tree. The default run uses a fixed set, so a new test class runs only with `--changed` or `--all`. `--changed` also adds the tests that cover changed filter lists, ad-block assets and content scripts (one `extra tests:` line per rule hit) and the unedited tests that use a class or composable declared in a changed main file (`tools/related_tests.py`, one `related tests:` line per file; a hub file such as `BrowserUiState.kt` pulls ~40 classes); It also runs Android Lint when a changed path is a manifest, `res/`, `*.gradle.kts`, the version catalog or a lint config; `--changed --dry-run` prints the selection and whether lint would run, without Gradle.
  - Each run ends with `==> Tests: N/M passed` and one `FAIL Class.test: message` line per failure (`tools/test_summary.py`); no need to open the XML reports. If the failures are linkage errors (`NoSuchMethodError`/`NoSuchFieldError`, or `NoClassDefFoundError` for an app class: stale incremental test classes), `verify.sh` deletes the two debugUnitTest Kotlin output dirs and reruns the tests once (every failure is one, or 5+ failures with 80% of them linkage errors). The rerun path is covered only by `tools/test_summary_test.py` so far: on its first real run, check that it reran and say so in PRO-81.
- **Visual UI Previews**: Run `rtk tools/preview.sh <TestName>` (e.g. `rtk tools/preview.sh BottomBarPreviewTest`) to render Compose previews to PNG in `build/` using Robolectric native graphics without deploying to a physical device.
- **Unit test target**: Always run `rtk tools/gradle_lock.sh ./gradlew testDebugUnitTest` (the lock keeps it from running beside another worktree's build). Never run bare `./gradlew test`, as `testReleaseUnitTest` fails without Robolectric release configuration. In coroutine tests `advanceUntilIdle()` skips `backgroundScope` work; use `runCurrent()` there.
- **Invariants**: Always verify `python3 tools/check_invariants.py` passes before finalizing changes. Hooks in `.claude/settings.json` (`tools/hooks/`) run it after every Edit/Write under `app/`, `tools/` or `TASKS.md` and report a new failure set once, and refuse edits to generated files (filter-list assets, `resources.json`, `scriptlets.js`, Room schemas), naming the generator to run instead.
- **On-Device Checks**: Use `rtk tools/device.sh <cmd>` instead of hand-written adb chains: `wake` (fails fast when the phone is locked: ask the user to unlock; it also sets the screen timeout to 30 min, because `stayon usb` holds only on USB power, and `sleep` puts the saved timeout back), `install` (records the build in `build/device/installed.txt`; `open`/`tap`/`tapui`/`eval`/`ui`/`log`/`visible`/`pages` then warn on stderr when the working tree is newer than that build, and never fail), `open <url>` (quotes URLs safely), `caller`, `back`, `top`, `visible`/`pages` (which WebView page is on screen, via CDP), `eval <url-prefix> <js>` (run JS in that page, prints JSON; `CDP_GESTURE=1` runs it as a user gesture, which is not enough for `requestFullscreen()` ("not granted"): inject a button whose handler calls it and press it with `tap <url-prefix> <selector>`; `location.origin` comes from the URL, read `self.origin` for a sandboxed page), `ui` (labelled nodes on screen), `tapui <label>`, `tap`/`swipe` (`tap <url-prefix> <css-selector>` taps an element's centre with a real touch, so the page sees a user gesture), `taps x1,y1 x2,y2 ...` (rapid taps at device pixels, all sent in one `adb shell` call with no round trip between taps; not for dock tabs: the dock can lose a tap right after a tab switch (PRO-115, accepted), so tap one tab, confirm it with `visible`, then tap the next), `serve` (the ad-block fixture at `http://127.0.0.1:8765/` via `adb reverse`, and loads its filter list into the debug app), `reset` (wipe the debug app's data), `secure off|on` (debug build: let `shot` capture incognito; FLAG_SECURE back on with `on`), `log <regex>`, `shot` (downscaled). Prefer `top`/`visible`/`log`/`ui` over screenshots. Put lock-screen checks last: after a lock the user must unlock the phone; test with Home where it covers the same path. Run `rtk tools/smoke.sh` after any change to WebView attachment, tab switching, intents or the Activity; it checks the on-screen page, the task stack and intent delivery and prints PASS/FAIL. Run `tools/device.sh sleep` when done. Never drive `com.jestk.browser` (the user's own install); the scripts refuse it.
- **Shell and tool calls**: the shell is zsh, so quote globs and URLs (`--include='*.kt'`, `'https://a/?q=1'`), or it fails with "no matches found". In auto mode send a Bash command on its own, not in parallel with another call: otherwise both may come back with "no verdict". Linear `save_issue`/`save_comment` are allowlisted in `.claude/settings.local.json` (they skip the auto-mode classifier), so batch them in one message; other Linear writes (deletes) still go one per call.
- **Large files and refactoring**: Map a big file with `python3 tools/outline.py <file>` (members with line ranges; `--groups name=a-b ...` prints calls between groups for planning a split) and read it in parts. Review a move-only refactoring with `python3 tools/move_check.py <base> [<head>] [--sub OLD=NEW]`: moved lines cancel out, only real changes are listed. Delegate the moving itself to the `refactor-mover` agent (`.claude/agents/refactor-mover.md`, Sonnet) with a plan section and a base commit; keep design and review in the main session.
- **Parallel agents**: Gradle builds run one at a time: `tools/verify.sh`, `tools/preview.sh` and `tools/device.sh install` take a repo-wide lock (`tools/gradle_lock.sh`, a directory in the shared git dir), so a second worktree's build prints "waiting" and starts when the first ends (two parallel builds stalled the 8 GB machine: a 34 min preview run and a Kotlin OOM; `GRADLE_LOCK=0` skips the lock). A bare Gradle command goes through the same lock as `tools/gradle_lock.sh ./gradlew …`. On this 8 GB machine three parallel agents ran the Kotlin daemon out of memory (`OutOfMemoryError`); if it happens, rerun with `LOW_MEM=1 tools/verify.sh …` / `LOW_MEM=1 tools/preview.sh …` (in-process Kotlin compile, 3 GB heap, 2 workers; pass the same flags to a bare Gradle run). Delegate coding tasks to the `prosto-coder` agent type (`.claude/agents/prosto-coder.md`, Sonnet; pass `model: "haiku"` for shell/Python harness work): it carries these standing rules, so the brief only needs the task. Tell any other delegated agent to edit code with Write/Edit (not heredoc or Python edits) and to run one command per Bash call: the worktree guard rejects compound commands. Ask it to list the platform assumptions its design relies on (WebView, Chromium, Android behaviour): those become the first device checks, which the `prosto-device` agent (`.claude/agents/prosto-device.md`, Sonnet, main checkout, one at a time) runs from the orchestrator's checklist. `tools/worktrees.sh list` shows every worktree with its merge state. **Do not keep old worktrees or branches:** after the last merge of a session, run `tools/worktrees.sh prune-merged --yes`; it removes the merged clean worktrees and deletes every local branch merged into `main` (only branches already contained in `main`, so unmerged or dirty work is never lost). It keeps `fresh` worktrees, whose branch has no commits of its own: an agent may have just started there. So prune only when no agent of this or another session is still running. A new worktree lacks the git-ignored `local.properties` and `TASKS.md`; `tools/verify.sh` and `tools/preview.sh` copy them from the main checkout (`tools/ensure_worktree_files.sh`), but copy them by hand before a bare Gradle run.
- **On-Device WebView Debugging**: See [`.agent/skills/adb-webview-testing/SKILL.md`](.agent/skills/adb-webview-testing/SKILL.md) for ADB port forwarding, CDP WebSocket tracing, cookie/storage inspection, and headless Chrome DevTools commands.
- **DuckDuckGo Android Reference**: See [`.agent/skills/duckduckgo-reference/SKILL.md`](.agent/skills/duckduckgo-reference/SKILL.md) for module paths, GitHub lookup recipes, and adaptation guidelines when implementing WebView edge cases, web compatibility, or privacy features.

### 3. Post-Implementation Reflection & Retrospective (Анализ работы и ретроспектива)
- After successfully implementing and verifying non-trivial fixes or features, conduct a brief retrospective analysis of the work done:
  - **Friction & Bottlenecks**: Identify what slowed down investigation or testing (e.g., ambiguous repro steps, long test feedback loops, obscure platform quirks).
  - **Mechanical Prevention**: Consider if this category of bug or regression can be prevented mechanically in the future (e.g., via `tools/check_invariants.py`, unit test invariants, or architectural seams).
  - **Process / Tooling Enhancements**: Suggest or implement concrete improvements to scripts, guidelines, or invariant checks so future tasks are faster and safer.
  - **Update LESSONS.md**: Use `python3 tools/harness_reflect.py add` to record new gotchas when relevant (observing the 10-12 active lesson budget).
- **End of every successful session** (not only non-trivial fixes): before the final report, analyse the session as a whole: what got in the way, what could have gone better, and what in the harness (scripts, invariants, docs, agent prompts) would make the next session faster or safer. Fix the small ones right away: inline while the session is still short (a few dozen calls); in a long session (e.g. after `/orchestrate`) every inline call re-reads the whole context, so hand them together to one Haiku `prosto-coder` agent instead. File every other one in Linear: team PRO, labels `agent`, `harness` and `Improvement` (or `Bug`), status Todo, one issue each; search for a duplicate first. There is no local harness task file.
- **Bugs and improvements found along the way**: anything you notice outside the task at hand (a bug in nearby code, a missing rule, a test or harness gap, a design idea) goes to Linear before the session ends, not only into the final report. One issue each, team PRO, labels `agent` plus `Bug` or `Improvement`, and also `harness` when it concerns the harness (scripts, invariants, test tooling, docs, skills, agent prompts); status Todo; search for a duplicate first (`list_issues` with a query) and link related issues. Add the label `verif` only when the problem is confirmed (reproduced, seen on a device, or proven in code with the evidence written in the issue) and needs no further verification before work starts; leave it off guesses and ideas that still need measuring, and say in the description which it is.

### 4. Token Economy for Orchestration and Subagents
The full pipeline (Linear Todo → triage → questions → delegation → review/merge → device checks → Linear) is the living skill [`.agent/skills/orchestrate/SKILL.md`](.agent/skills/orchestrate/SKILL.md) (`/orchestrate`); a better practice found later goes there first, with its evidence in [`PRACTICE_LOG.md`](.agent/skills/orchestrate/PRACTICE_LOG.md) next to it (prune stale details there). The rules below are its measured core.
Measured on 2026-11-18 over seven Linear tasks with `python3 tools/agent_cost.py <agent transcript.jsonl>`, which prints the turns, the token counts and one weighted cost figure per run. Every API turn re-reads the agent's whole context from the cache, so cost ≈ turns × context size; cache reads were 70–85% of every run.
- **Brief with discipline rules (best result).** Paste this block into every coding-agent brief: *"Batch all independent Read/Grep/Edit calls of a step into ONE message. Map a big file with `python3 tools/outline.py` and read it by offset/limit; never read a >300-line file whole. Don't re-read a file after editing it, and don't re-run a passing check. Keep narration minimal."* With it, a mid-size Kotlin feature (PRO-56) took 20 turns and 0 whole-file Reads at 328k units. Comparable runs without the block took 23–45 turns and 462k–773k units, about 30–55% less.
- **Pre-locate files in the brief.** The orchestrator greps once and names the files, entry points, line ranges and existing APIs to reuse (e.g. `Modifier.swipeToDismissPill(resetKey=, onDismiss=)`). Paste the issue text and decisions into the brief instead of letting the agent call Linear: MCP schemas and answers are expensive.
- **Fresh agent over continuing one.** Continuing an agent via SendMessage carries its whole history into every new turn. A follow-up task given to a finished agent cost ~750k units, against 330–460k for a fresh agent with a brief that names the earlier work's API. Continue an agent only for a short fix-up of its own work.
- **Model per task.** Shell/Python harness work fits Haiku: PRO-51+52 came out correct at about a third of the Sonnet price. Kotlin/Compose features go to Sonnet. The orchestrator (Opus) keeps design decisions, review and merging.
- **Group and order by files.** Small tasks that touch the same files go to one agent; independent ones run in parallel worktrees, at most two Gradle users at a time. Instruct an agent to add only a call line to a shared host file (e.g. `AppNotificationPills.kt`) and to put the new code in its own file: rebases then stay conflict-free.
- **Orchestrator side.** Ask the user's design questions before delegating, in one `AskUserQuestion` call. Do small fixes (a few lines) yourself instead of a new agent round. Review a branch with `git diff --stat main...<branch>` plus the key files only. Merge with `git -C <worktree> rebase main` and `git merge --ff-only`, then rerun `tools/verify.sh --changed`: rebases of parallel branches can break the 500-line cap (it happened to `BrowserViewModel.kt`). Ask each agent for a report of 15 lines or fewer.

## Architectural Invariants & Code Standards

### Favicon Subsystem
- **Single Source of Truth**: The only valid event for receiving a website's favicon is `WebChromeClient.onReceivedIcon(view, icon)`.
- **Never extract favicons in `WebViewClient`**: In Android Chromium WebView, `onPageStarted(view, url, favicon)` and `view.favicon` in `onPageFinished` frequently return the favicon of the *previous* page loaded in that WebView during cross-domain navigation.
- **Domain Guard**: Always verify `isSameDomain(tab.url, pageUrl)` before updating a tab's favicon or domain cache.
- **Cross-Domain Navigation**: Upon navigating to a different domain, always evict stale per-tab favicon files (`FaviconManager.deleteTabFavicons(tabId)`).

### Compose & WebView State
- **No stale closures**: In `WebViewContainer`, do not use unkeyed `remember { ... }` blocks that capture volatile outer composition values (`currentTab`, `targetUrl`). Prefer `rememberUpdatedState` or look up current tab dynamically from `currentUiState.tabs.find { it.id == id }`.
- **No Blur**: Strict prohibition on `Modifier.blur()` and `dev.chrisbanes.haze` across the entire app. Live `WebView` inside `GraphicsLayer` or dynamic blur causes severe screen flicker on Android 12+.
- **Domain Layer Purity**: Domain layer must remain free of Android framework UI types (`android.view.*`, `android.widget.*`, `android.graphics.*`) and Compose types. Domain models must remain pure Kotlin.

### Anti-Bot & Content Scripts Standards (Cloudflare / Turnstile / WAF)
- **UserAgentMetadata Purity**: Never construct synthetic brand lists or artificial GREASE versions from scratch. Mirror DuckDuckGo: read native `WebSettingsCompat.getUserAgentMetadata(settings)`, keep Chromium's genuine GREASE brand, versions, and entropy fields untouched, and only map `"Android WebView"` -> `"Google Chrome"`.
- **Security Challenge Exemption**: Never inject ad-blocking, auto-consent, or user scripts into authentication and security challenge domains (`challenges.cloudflare.com`, `cloudflarecaptcha.com`, `/cdn-cgi/challenge-platform`).
- **DOM Stealth & Function Integrity**: Injected scripts must leave no trace a page can enumerate. Do not add `window.*` names at all (`enumerable: false` still shows in `Object.getOwnPropertyNames(window)`), and do not replace native functions (`matchMedia`, `screen.orientation.lock`, `window.open`): an own `toString` override is bypassed by `Function.prototype.toString.call(fn)`. If a native must be patched, patch it only while it is needed (see the fullscreen-only orientation bridge in `assets/scripts/content_bootstrap.js`). Theme goes through the Activity theme (`UiModeManager.setApplicationNightMode`), never through a `matchMedia` polyfill. Verify with the CDP probe in `docs/specs/2026-11-codebase-review.md` §5; `tools/check_invariants.py` enforces the basics.
- **Ad-Block List**: `app/src/main/assets/adblock_domains.txt` is generated by `tools/build_adblock_list.py` from the standard lists in `tools/filterlists/lists.json`; never edit it (or `adblock_popup_hosts.txt`, `assets/filters/**`, `assets/adblock/resources.json`) by hand: regenerate with `tools/update_filterlists.py` / `tools/build_adblock_resources.py`. The one hand-edited list is `tools/filterlists/prosto.txt` (site fixes the upstream lists lack, `"local": true` in `lists.json`): edit it there, then run `tools/update_filterlists.py --offline`. Never block a site on its own pages or the main-frame document.

### Code Hygiene & Localization
- **English-Only Documentation & Artifacts**: All project documentation, architectural decision records (ADRs), technical plans, task artifacts, code comments, and commit messages must be written strictly in English. Russian is reserved exclusively for user-facing localization resources (`res/values-ru/strings.xml`) and conversational dialogue when addressed by the user in Russian.
- **UI Localization (Zero Hardcoded Strings)**: Never hardcode user-facing strings in composables or dialogs. Every string must exist in both `res/values/strings.xml` and `res/values-ru/strings.xml`, accessed via `stringResource(R.string.*)`.
- **Zero Dead Code Policy**: Do not leave commented-out code blocks in source files. Delete dead code completely.
- **Modularity**: Keep files focused (<400–500 LOC). Separate reusable state holders, popups, and auxiliary rows into dedicated files. `tools/file_size_ratchet.py` (part of the invariants) fails a new source file over 500 lines and any file listed in `tools/file_size_baseline.json` that grows; put new code in a new file. After splitting a large file, run `python3 tools/file_size_ratchet.py --update` to lower its baseline. A file at its baseline cannot grow at all: before adding lines, extract a self-contained piece first (e.g. `engine/CssColorParser.kt` out of `JestkWebViewClient.kt`). New `BrowserUiEvent` types go in their own file next to it (e.g. `ui/viewmodel/BackgroundPlaybackEvents.kt`).
